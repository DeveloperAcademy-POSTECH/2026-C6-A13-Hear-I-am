## 2. 기술 후보 비교

VAD는 말소리의 존재를 감지하는 기능, ASR은 말소리를 글자로 바꾸는 기능이다. 아래 후보는 역할이 다르므로 단순한 성능 순위가 아니다. 단순 음량 상승이나 박수 검출을 사용자 발화 감지로 간주하지 않는다. VAD만으로 발화자가 착용자 본인인지 구분할 수도 없다.

| 후보 | 확인한 기능 | 제약·추가 검증 | 이번 선택 |
| --- | --- | --- | --- |
| 1. Apple `SFSpeechRecognizer` | 마이크 버퍼 전사, 부분·최종 결과, 최초 발화 감지 delegate, 한국어 로케일 설정, 기기 내 인식 지원 조회 | 기기·언어의 실제 가용성 확인 필요. 장시간 단일 작업 대신 작업 교체 필요. 감지 지연과 정확도 보장 없음 | **현재 PoC의 ASR·시작 감지 수단** |
| 2. Apple `SpeechAnalyzer` + `SpeechTranscriber` | iOS 26 이상에서 기기 내 실시간 전사, 임시·확정 결과, 언어 모델 설치 관리 | 기기·지원 로케일·설치 상태를 런타임 검사. 현재 최소 지원 iOS 17과 함께 쓰려면 별도 구현 필요 | 후속 동일 조건 비교 후보 |

## 3. 이번에 선택한 구성

`AVAudioEngine 입력 → SFSpeechRecognizer(ko-KR) → 최종 문장 → VoiceCommandParser → 기존 안내 상태·복귀 경로 검사 → 안내 실행`

선택 이유:

- 현재 iOS 17 지원 범위를 유지하며 기본 프레임워크로 검증할 수 있다.
- `speechRecognitionDidDetectSpeech`로 작업의 최초 발화를 감지하고 띠링 이벤트를 연결할 수 있다.
- 부분 인식은 화면에 보여주고, 명령 실행은 최종 결과로 제한할 수 있다.
- 이번 명령은 다음·계속·멈춰·다시 듣기·지점 복귀처럼 범위가 작아 언어 모델 없이 결정적으로 처리할 수 있다.
- 기존 위치·기물·경로 검증을 명령 처리 이후에도 그대로 적용할 수 있다.

### 인식 가용성·권한

첫 음성 기능 진입 때 마이크와 Speech 권한을 요청한다. 앱 흐름에서 인식 오류가 전달되면 입력을 종료하고 수동 재시도를 요구한다. 서비스 내부의 재시도 설정과 별개로 앱이 오류 후 자동으로 다시 듣지는 않는다. 권한 거절·제한·한국어 인식 불가·기기 내 인식 미지원은 화면에 이유를 표시하고 버튼 흐름을 유지한다.

`ko-KR` 인식기 생성만으로 사용 가능하다고 판단하지 않는다. 인식기의 가용성과 `supportsOnDeviceRecognition`을 확인하고, 요청에는 `requiresOnDeviceRecognition=true`를 지정한다. 미지원 기기에서 서버 인식으로 자동 전환하지 않는다. 이번 구현은 언어 모델을 직접 내려받는 별도 준비 UI를 제공하지 않는다.

- [Apple 음성 인식 권한과 SpeechAnalyzer의 차이](https://developer.apple.com/documentation/Speech/asking-permission-to-use-speech-recognition)
- [기기 내 인식 요청 조건](https://developer.apple.com/documentation/speech/sfspeechrecognitionrequest/requiresondevicerecognition)
- [지원 로케일과 현재 가용성 차이](https://developer.apple.com/documentation/speech/sfspeechrecognizer/supportedlocales())

### 발화·종료 처리

- 하나의 인식 작업에서 발화 감지 띠링은 한 번만 요청한다. 발화 delegate보다 부분 문장이 먼저 도착하는 경우도 처리한다.
- 띠링이 울릴 때 이미 들어오던 음성을 버리거나 인식 작업을 교체하지 않는다.
- 부분 문장은 UI 표시용이며 이동 명령 실행에 사용하지 않는다.
- 잠정 종료 시 입력을 마감한 뒤 확정 결과를 기다린다. 최종 결과가 없으면 부분 문장을 대신 실행하지 않는다.
- 세션·인식 작업마다 식별자를 부여해 취소·이전 단계의 늦은 결과와 중복 최종 결과를 무시한다.
- 숫자·지점명은 앱의 실제 저장 지점 번호로 해석한다. 복수 지점을 포함하거나 지원 문법과 맞지 않는 문장은 재질문한다.

`contextualStrings`는 저장 무대 이름과 짧은 명령 인식을 돕는 힌트다. 해당 문장만 인식하게 만드는 강제 문법이나 정확도 보장은 아니다. [Apple contextualStrings](https://developer.apple.com/documentation/speech/sfspeechrecognitionrequest/contextualstrings)

## 4. 오디오 사용 원칙

음성 입력 활성 시에만 공용 오디오 세션의 입력 사용권을 얻는다. 기존 안내 음성·신호음이 재생될 때 입력 세션을 출력 전용으로 덮어쓰지 않도록 한다. 입력을 종료하면 기존 출력 구성을 복원한다.

- 입력·출력을 함께 쓰는 동안 `playAndRecord`와 voice processing을 사용한다.
- voice processing 준비에 실패하면 자동 듣기를 비활성화하고 재시도·버튼 흐름을 제공한다.
- **이번 구현은 앱 TTS와의 반이중 방식이다.** 앱이 말하는 동안 현재 인식 턴을 취소하고 입력 버퍼를 전사기에 전달하지 않는다. 안내 음성이 끝나면 다시 듣는다.
- 따라서 앱의 설명을 말로 끊는 완전한 동시 대화는 아직 지원하지 않는다. 이동 중에는 안내 음성 사이의 구간에서 자동 발화 감지가 동작한다.
- 짧은 듣기 띠링 때문에 인식을 억제하지 않는다. 사용자의 첫 음절을 버리지 않기 위한 구분이다.
- 실전 시작·화면 종료에는 입력 tap 제거, 엔진 정지, 인식 취소, 지연 재시작 작업 취소까지 수행한다.
- 위치·기물 문제로 기존 이탈 복귀 안내가 진행되는 동안에는 추가 음성 요청을 받지 않는다.
- 연결 변경·시스템 오디오 중단·백그라운드에서는 입력을 멈추고 수동 재시도를 요구한다.
- VoiceOver는 앱 TTS와 별개의 출력이다. VoiceOver의 음성과 조작이 인식에 미치는 영향은 실기기 검증 대상으로 남긴다.

에코 처리는 자기 음성 오인식을 줄이는 기술이며 모든 출력 장치·공간·소음에서 완벽한 제거를 보장하지 않는다. A2DP는 출력 전용이고 HFP는 마이크 입력을 지원하므로, 이어폰 마이크 사용 시 실제 오디오 경로와 음질을 확인한다.

- [Apple AVAudioEngine voice processing](https://developer.apple.com/videos/play/wwdc2019/510/)
- [Bluetooth A2DP와 HFP 경로](https://developer.apple.com/documentation/avfaudio/avaudiosession/categoryoptions-swift.struct/allowbluetootha2dp)
- [오디오 경로 변경 처리](https://developer.apple.com/documentation/avfaudio/responding-to-audio-route-changes)
- [앱 음성 합성과 접근성 음성의 역할](https://developer.apple.com/videos/play/wwdc2020/10022/)

| 홈 | 별도 ‘말로 안내 시작’ 버튼 | 버튼 누르기 | 기존 일반 안내 진입과 구분해 실험 화면 열기 |
| 첫 준비 | 권한·입력 준비 또는 오류 상태 | 최초 권한 응답 | 권한과 입력 준비 확인. 실제 듣기 준비가 되었을 때 시작 띠링 |
| 저장 무대 선택 | 기존 저장 무대 목록, 현재 선택 | 무대 이름 / ‘두 번째’ / ‘2번 무대’ / 화면 선택 | 하나의 저장 항목으로 확정되는 경우 선택. 이름 중복은 화면에서 구분 요청 |
| 사용 방식 | 연습용·실전용 선택 | ‘연습용’ / ‘실전용’ | 모드 확인 음성. 실전은 시작 후 마이크가 꺼짐을 설명 |
| 다음 | 선택된 무대·사용 방식 | ‘다음’ | 무대와 모드가 모두 선택된 경우 공간 복원 시작 |

현재 음성 검색 대상은 기존 저장 무대 목록이다. 외부 공연장 검색·공간 카탈로그 전체 검색·자유로운 대화 추천은 구현하지 않는다. 한 번에 한 가지 요청을 받으며, 이름이나 순서가 불명확하면 자동으로 임의 선택하지 않는다.

### B. 기존 준비 절차 통과

1. **공간 복원:** 휴대폰을 손에 들고 저장 공간을 찾는다. 복원 중에는 음성 명령으로 검증을 건너뛰지 않는다.
2. **확인점:** 조준점을 저장 확인점에 맞춘 뒤 ‘다음’으로 확인을 요청한다. 기존 `canVerify`와 AR 검증이 만족되어야 한다.
3. **방해금지·착용 안내:** 기존 방해금지 안내와 허리 앞 세로 고정·카메라 방향 설명을 제공한다. 앱이 시스템 방해금지 설정을 직접 변경하거나 설정 완료를 자동 검증하는 기능은 아니다.
4. **착용 완료:** ‘착용 완료’ 또는 ‘다음’을 받아도 위치 추적과 기존 단계 조건을 확인한다. 8초 카운트다운은 없다.
5. **출발 준비:** 지정 출발점·몸 방향·기물 및 동선 조건을 기존 규칙으로 확인한다.
6. **시작:** ‘시작’ 또는 ‘계속’이 들어와도 출발 조건이 유효할 때만 시작한다. 시작 안내 중 조건이 바뀌면 안내를 강행하지 않는다.

### C. 연습 중 발화와 P2 복귀

예시 전제: P2에 이미 도착한 뒤 P3 이후의 구간으로 진행 중이며, P2가 출발점이나 최종 도착점이 아닌 내부 지점이다.

1. **일반 이동:** 기존 방향·거리·기물 신호로 안내한다. 앱 TTS가 말하지 않는 동안 발화 감지를 대기한다.
2. **사용자 발화 감지:** 현재 안내 진행을 보류하고, ‘듣고 있어요’ 화면과 띠링을 제공한다. 사용자는 잠시 멈춘다. 첫 발화는 같은 인식 턴에 계속 들어간다.
3. **문장 표시:** ‘P2 지점으로 다시 안내해 줘’의 부분 문장을 표시한다. 부분 결과만으로 이동을 시작하지 않는다.
4. **최종 해석:** 한 지점으로 확정되는 지원 명령인지 검사한다. ‘P2 말고 P3’와 같은 모호한 복수 지점 요청은 자동 실행하지 않는다.
5. **복귀 사전 검사:** 연습 모드·안내 시작 여부·최신 위치·현재 동선·이미 방문한 내부 지점·역방향 각 구간의 통과 조건을 확인한다.
6. **복귀 안내:** ‘P2로 다시 안내합니다’라고 말하고, 저장 경로에서 지나온 지점을 순서대로 되짚는다. 현재 위치에서 P2로 직선 지름길을 만들지 않는다.
7. **도착 확인:** 기존 도착 반경·유지 시간 조건을 충족하면 P2 도착 상태로 보류한다. 복귀를 원래 공연 전체 완료로 기록하지 않는다.
8. **도착 음성:** ‘P2 지점에 도착했어요. 계속이라고 말씀하면 다음 지점으로 안내해요.’라고 알려준다.
9. **명시적 재개:** ‘계속’을 받으면 현재 위치와 재개 가능 상태를 검사하고 P3 방향의 원래 순서로 진행한다.

화면은 ‘말씀하시면 들을게요’, ‘듣고 있어요’, ‘말씀을 확인하는 중’, ‘P2로 다시 안내 중’, ‘P2 도착·계속 대기’를 구분한다. 인식 오류·권한 거절·연결 끊김은 재시도 버튼과 기존 터치 조작을 함께 제공한다.

### D. 실전용 마이크 정책

- 준비 단계에서는 말로 무대 선택·현장 확인·착용·출발 요청을 진행할 수 있다.
- **안내 시작 단계에 들어갈 때** 인식 task와 입력 tap·엔진·예약된 재시작을 중지한다.
- 실전 안내가 시작된 이후에는 일시정지·추적 중단·재개 상태에서도 음성 인식을 켜지 않는다.
- ‘실전 안내 중 · 음성 인식 꺼짐’을 표시한다. 실제 마이크가 켜진 채 결과만 무시하는 상태는 허용하지 않는다.
- 실전 중 조작은 기존 화면의 일시정지·재개·종료를 사용한다. 연습 모드로 말만 해서 전환하지 않는다.

### E. 예외 처리

| 상황 | 처리 |
| --- | --- |
| 인식 불가·권한 거절 | 자동 진행하지 않고 이유·재시도·버튼 흐름 제공 |
| 알 수 없는 명령·복수 지점 | 안내 보류 상태에서 한 가지 요청을 다시 말하도록 안내 |
| 아직 방문하지 않은 지점·출발점·최종점 | 이번 실험의 지원 범위를 설명하고 복귀 요청 거절 |
| 현재 위치 또는 방향 불명확 | 복귀 실행 금지, 기존 확인점·복원 흐름 이용 |
| 역방향 통과가 막힌 단상·기물 | 경로를 임의 변경하지 않고 이유를 안내 |

| 복귀 지점 도착 후 | ‘계속’ 또는 기존 재개 버튼 전에는 다음 지점으로 자동 진행 금지 |

## 6. 경로와 기록의 범위

### 복귀 허용 조건

- 저장된 유효 경로의 안내가 시작된 상태여야 한다.
- 현재 목표보다 앞서 방문한 내부 지점만 허용한다.
- 출발점·최종점·미방문점·복귀 진행 중 다른 복귀는 이번 범위에서 제외한다.
- 현재 위치가 유효한 동선 위에 있어야 하고, 역방향 모든 구간의 기물 통과 방향·여유 공간을 검사한다.
- 검사 실패 시 원래 목표를 임의로 바꾸지 않는다.
- 저장된 원본 경로를 수정하지 않는다. 복귀 상태와 앞으로 재개할 상태를 별도로 유지한다.

### 기록에 남기는 것

기존 위치·시간·방향·목표 지점·상태 샘플 수집을 사용한다. 다음 이벤트로 사용자의 요청과 복귀 흐름을 구분한다.

| 이벤트 | 의미 |
| --- | --- |
| `voice_listening` | 발화 감지로 듣기 상태 진입 |
| `voice_command` | 최종 인식 문장 수신 |
| `rehearsal_return_requested` | 복귀 목적지와 첫 역방향 목표 |
| `rehearsal_return_arrived` | 요청한 복귀 지점 도착 |
| `rehearsal_forward_resumed` | 복귀 뒤 원래 순서로 다시 진행 |

이번 구현에서 사용자의 마이크 원본 음성을 녹음 파일로 저장하지 않는다. 인식 문장과 요청 이벤트는 기존 신호 로그의 검증 자료가 될 수 있으므로, 외부 공유 시 필요한 범위만 발췌한다.

**기존 리플레이 분석에는 순방향 목표 진행을 전제로 한 도착·구간 해석이 남아 있다.** 복귀로 목표 번호가 감소하는 경우를 새로운 연습 회차나 정상 역방향 이동으로 정교하게 분리하는 분석은 이번에 완성하지 않는다. 전체 경로에 대한 기존 이탈 요약을 ‘이번 연습 구간의 정확한 평가’로 표현하지 않는다.

이번 범위에 포함되지 않는 것:

- 회차별 점수·구간별 좌우 이탈 시간·이전 회차 비교·연습 종료 음성 코칭
- 자유로운 경로 생성, 자동 우회 경로, 카메라 AI로 보행 가능 여부 판단
- 완전한 동시 대화, 주변 사람과 착용자 음성의 자동 구분
- 클라우드 ASR·대화 서버·생성형 AI 백엔드
- 공간 전체 검색과 자유로운 공연 추천

## 7. 실기기 검증표

다음은 합격 기준과 측정 계획이다. **아직 수행 결과가 아니다.** 현장 시험은 준비한 저장 경로와 조력자 확인 아래 진행하며, 잘못된 지점 실행이 한 번이라도 발생하면 원인을 해결한 후 다시 시험한다.

- 발화 시작 시각, 감지 시각, 띠링 시각, 발화 종료 시각, 최종 결과 시각, 명령 적용 시각

- 첫 음절 누락, 잘못된 지점 선택, 무응답, 오탐, 중복 명령, 중복 띠링 횟수

- AR 추적 상태·위치 최신성, 경로 사전 검사 결과, 도착 확인·계속 재개 결과

## 9. 기기에서 확인할 순서

1. Xcode에서 이 작업 폴더의 `Hear-I-am.xcodeproj`를 열고 같은 iPhone에 설치한다.
2. 기존 방식으로 출발·P1·P2·P3·도착이 있는 공간과 경로를 준비한다. 역방향으로 통과할 수 없는 기물은 없는 경로부터 시작한다.
3. 홈의 **말로 안내 시작**을 누르고 최초 마이크·음성 인식 권한을 허용한다. 앱 설명 뒤 준비 띠링을 기다린다.
4. 저장한 무대 이름 또는 ‘첫 번째’, ‘연습용’, ‘다음’을 순서대로 말한다. 현장 확인·착용·출발 조건을 충족한 뒤 ‘시작’한다.
5. P2를 지나 P3 방향으로 이동 중 앱 음성이 끝난 구간에서 ‘P2 지점으로 다시 안내해 줘’라고 말한다. 띠링 후 멈추고, 요청 확정과 복귀 안내를 확인한다.
6. P2 도착 안내 후 자동 전진하지 않는지 확인하고 ‘계속’으로 P3 안내를 재개한다.
7. 새 세션에서 ‘실전용’을 선택하고 안내 시작 이후 일시정지·복원·재개 중에도 음성 입력이 다시 켜지지 않는지 확인한다.
8. 앱을 배경으로 보냈다가 돌아오면 마이크가 꺼져 있어야 한다. ‘다시 말하기’로 수동 재시작한다.

기기 내 한국어 인식을 사용할 수 없다는 안내가 나오면 자동으로 서버 인식을 켜지 않는다. 해당 기기·iOS·권한 상태를 검증표에 남기고 기존 버튼으로 진행한다.
